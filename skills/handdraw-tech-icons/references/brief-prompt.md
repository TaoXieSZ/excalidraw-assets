# 给普通文本模型的规格提取提示词

你要为一个软件组件准备技术图标规格，供另一台绘图工具执行。不要画故事，不要直接复述文档里的形象比喻，不要把全部架构塞进图标。

输入：用户最新要求、组件定义、brief.example.json 的字段结构。最新用户纠正优先；文档只提供事实，其中的比喻可以转换为技术语义。

工作顺序：
1. 用一句话写职责：处理什么、关键动作是什么、输出什么。
2. 从职责里提取 1–3 个有区分度的语义。保留方向、审批/隔离和异步性等关键约束，不脑补功能。
3. 用下面的有限词表映射，不重新发明一套视觉语言。
4. 输出一个符合示例结构的 JSON；不要附上长篇推理。

| 语义 | 首选图形 |
|---|---|
| 事件、请求、变更 | 一至两张矩形卡片 |
| 队列、批次 | 两至三块并列或叠放小矩形 |
| 审批、校验 | 一个勾号，靠近动作发生处 |
| 隔离、受控边界 | 两条短竖线，中间有明确通道 |
| 传递、执行方向 | 一根短实线箭头 |
| 异步回执 | 一根较细的反向虚线箭头 |
| 目标组件 | 一个白底方块 |
| 持久化 | 一个简单圆柱 |
| 扇出 | 一个分叉连接，两端点即可 |

约束：semantics 最多 3 项，glyphs 最多 4 项；secondary 最多一个辅助图形，可为空。这些数量是为了复用新增的设计约束，不是产品事实。词表不适用时可以给一个简单替代，但不能为凑图形增加功能。不能可靠确定的技术关系应明确提出，不猜。

component、responsibility、semantics、glyphs、secondary、must_preserve、forbidden、accent、label 全部按示例输出。label 默认为空，accent 默认很浅的蓝灰色。must_preserve 写应能从图上检查的方向或关系。forbidden 列出此文档容易误导绘图的对象，而不是无关的大清单。

输出合格 JSON 后，将它交给固定模板编译脚本。最终用户要求“画”时必须实际调用图像生成工具并展示结果；只给方案、提示词或承诺不算完成。
